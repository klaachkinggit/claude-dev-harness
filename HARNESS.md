# HARNESS.md — Capability Map (for agents)

> **If you are an AI agent told to use this repo as a harness, read this file.**
> It describes what the harness provides and how each layer maps to *your* tool's
> mechanism. If your tool isn't listed, use the generic column and adapt.

## Mental model

The harness has **layers**. Some are universal (work everywhere). Some are
tool-specific (the *protection* is universal, the *mechanism* differs per tool).

| Layer | What it does | Universal? |
|-------|-------------|-----------|
| Rules | Behavioral contract (how to write code) | ✅ content universal, filename per tool |
| Prompts | Reusable workflow templates | ✅ plain markdown, paste anywhere |
| MCP | Tool/data servers (github, fs, git, browser, db) | ⚠️ same servers, config format/path per tool |
| Git hooks | Block secrets, format, gate tests at commit/push | ✅ runs under any tool or human |
| CI | Same gates on GitHub | ✅ runs server-side regardless of agent |
| Runtime hooks | Block dangerous cmds / secrets *during* the session | ❌ Claude Code + Codex only (need a hook system) |
| Slash commands | Prompts wired as `/commands` | ❌ Claude Code + Codex only |
| Plugins | Curated skill packs | ❌ Claude Code only |

**Design principle:** anything that *can* be enforced at the git/CI layer is, so
protection holds no matter who writes the code. Runtime hooks are a faster
feedback copy of the same checks for tools that support them.

## Rules file — where your tool reads its instructions

| Tool | File | Env-var syntax in MCP |
|------|------|----------------------|
| Claude Code | `CLAUDE.md` | `${VAR}` |
| Codex CLI | `AGENTS.md` | none — forward by name (`env_vars`) |
| Cursor | `.cursorrules` + `.cursor/rules/*.mdc` | `${env:VAR}` |
| Windsurf | `.windsurfules` | `${env:VAR}` |
| Gemini CLI | `GEMINI.md` | `$VAR` |
| GitHub Copilot | `.github/copilot-instructions.md` | n/a (configured in VS Code) |
| Cline | `.clinerules` | varies |
| **Your tool not here?** | Copy `RULES.md` into your system prompt / instructions file | check your tool's docs |

All of these contain the same rules (`RULES.md`), regenerated by `sync-rules.sh`.

## MCP — getting servers into your tool

Single source of truth: `tools/gen-mcp.py`. It emits the right format/path:

```bash
python3 tools/gen-mcp.py claude    # → .mcp.json            (project root)
python3 tools/gen-mcp.py cursor    # → .cursor/mcp.json     (project)
python3 tools/gen-mcp.py codex     # → .codex/config.toml   (project, TOML)
python3 tools/gen-mcp.py windsurf  # → prints ~/.codeium/windsurf/mcp_config.json snippet
python3 tools/gen-mcp.py gemini    # → prints ~/.gemini/settings.json snippet
```

Servers provided: `github`, `filesystem`, `git`, `playwright`, and `db` (added
only if `DATABASE_URL` is set). **If your tool isn't an emitter:** read `.mcp.json`
(generic JSON schema) and translate it to your tool's MCP config format/location.
Adding a new emitter is one function in `gen-mcp.py`.

**Adding stack-specific servers** (Vercel, Docker, Stripe, Supabase, Sentry, …):
see PROFILES.md "MCP servers by stack" for verified picks, or discover live via
`registry.modelcontextprotocol.io`, awesome-mcp-servers, mcp.so, Smithery, PulseMCP.
Don't re-add what gen-mcp already provides (github, filesystem, git, playwright, db).

## Runtime hooks — Claude Code & Codex

Scripts live in `.claude/hooks/` (shared). They read the tool-call as JSON on
stdin and exit `2` to block.

- **Claude Code:** wired in `.claude/settings.json`.
- **Codex CLI:** wired in `.codex/hooks.json` (same scripts).
- **⚠️ Codex caveat:** the scripts expect `tool_input.command` /
  `tool_input.file_path` in the stdin JSON. Codex's hook schema mirrors Claude
  Code's but field names may differ by version. **Test before trusting:** send a
  known-bad command (e.g. recursive rm of root) and confirm it's blocked. If the
  field is absent, scripts **fail open** (no block) — so verify, don't assume.
- **Other tools (no hook system):** you don't get runtime blocking. The git
  hooks below cover the same ground at commit/push time.

Hook scripts:
| Script | Blocks / does |
|--------|--------------|
| `block-dangerous.sh` | recursive rm of root/home/cwd, `curl\|sh`, force-push main, fork bomb, mkfs, dd-to-disk |
| `protect-secrets.sh` | read/write/edit of `.env`, `.pem`, `.key`, credentials |
| `auto-format.sh` | prettier/black/ruff/gofmt/rustfmt on edited files |
| `log-bash.sh` | appends every command to `.claude/bash.log` |
| `pre-pr-gate.sh` | blocks PR creation if tests fail |

## Git + CI — universal enforcement (every tool, every human)

- `.githooks/pre-commit` — blocks committing secrets, auto-formats staged files.
- `.githooks/pre-push` — runs tests, blocks push on failure.
- Activate: `git config core.hooksPath .githooks` (apply.sh does this).
- Bypass once: `git commit --no-verify` / `git push --no-verify`.
- `.github/workflows/ci.yml` — secret scan + lint + test on GitHub push/PR.

This layer is the reason the harness is "model-agnostic on all aspects" even
though hooks/plugins/slash-commands aren't: the *guarantees* (no secrets, code
formatted, tests pass) hold at the git/CI layer regardless of which agent wrote
the code — Claude, Codex, a tool released next year, or a human.

## Skills — kept lean on purpose

Skill descriptions load into context every session; past ~1% of the context
window they get truncated and mis-activate. So the base bundles only:
- `caveman` — token reduction
- `find-skills` — discovers + installs any other skill on demand (`npx skills find`)

Everything else is **per-project**, not in the base. To add a skill pack for a
specific project (web, reporting, scraping, …) see **PROFILES.md**, or just ask
the agent *"find a skill for X"* (that triggers `find-skills`). Audit installed
skills periodically: if you haven't used one in two weeks, remove it.

## Prompts — workflow templates (universal)

`prompts/*.md` are plain markdown. Paste into any tool, or invoke as slash
commands where supported (Claude: `/grill-me`; Codex: drop into `~/.codex/prompts/`).

| Prompt | Use |
|--------|-----|
| `grill-me` | Requirements interview before large work |
| `tdd` | RED-GREEN-REFACTOR |
| `diagnose` | 8-step structured debugging |
| `to-issues` | Plan → vertically-sliced GitHub issues |
| `zoom-out` | System map before unfamiliar code |
| `handoff` | Compact session → HANDOFF.md |
| `security-scan` | OWASP Top 10 + secrets |
| `preflight` | Pre-ship checklist |
| `assess-capabilities` | Assess + install the skills, MCP servers & plugins a project/feature needs |
| `adopt-harness` | Adopt harness into an existing project + clean up its skills |

## If you're a brand-new tool with none of these mechanisms

Minimum viable adoption, in priority order:
1. Load `RULES.md` as your system instructions. (behavior)
2. Translate `.mcp.json` to your MCP config. (capabilities)
3. Ensure `git config core.hooksPath .githooks` is set. (enforcement — this is
   the safety net that doesn't depend on you supporting anything.)
4. Use `prompts/*.md` as templates for structured work.
That's 80% of the value with zero tool-specific features required.
